# Academy newsletter / Resend Broadcasts

Homepage signup, new account registrations, academy notice publication and custom broadcasts are connected to a persistent outbox. Admin → Emails contains Email history and Newsletter broadcasts tabs. Global newsletters do not appear in partner organization email history.

## Configuration

Run `pnpm db:migrate:newsletter` for each database used by the deployment. This additive, repeatable migration creates subscriber, campaign, attachment and webhook deduplication tables plus email permissions. It does not import historical users or send historical notices. Keep the existing migrations as well.

Set these server-only variables locally and in Vercel:

- `RESEND_NEWSLETTER_API_KEY`: Resend full-access API key. An existing SMTP API key can be reused if it has full access; a sending-only key cannot administer contacts and segments.
- `RESEND_NEWSLETTER_SEGMENT_ID`: ID of a dedicated **Academy Newsletter** segment in Resend. Only contacts in this segment receive broadcasts. Use current Contacts/Segments APIs, not deprecated audiences.
- `NEWSLETTER_FROM_ADDRESS`: verified sender, optionally `Kaizen Karate Academy <noreply@your-verified-domain>`.
- `RESEND_NEWSLETTER_WEBHOOK_SECRET`: signing secret from a Resend webhook configured at `https://www.hstuma.com/api/newsletter/webhook`.
- `NEXT_PUBLIC_APP_URL`: canonical HTTPS website origin used in email links (defaults to `https://www.hstuma.com`).

Select `email.sent`, `email.delivered`, `email.bounced`, `email.failed`, `email.delivery_delayed`, `email.complained`, `email.opened`, `email.clicked`, `email.suppressed`, `contact.updated` and `contact.deleted` events. Only signed raw-body webhooks are accepted; replayed event IDs do not duplicate history. Configure this endpoint instead of also sending the same events to the legacy `/api/webhook` endpoint, to avoid duplicate history entries. Provider bodies and credentials are never retained in history.

The webhook secret is a separate `whsec_...` value generated by Resend when the webhook is created. It verifies incoming event signatures; it is not the API key or SMTP password. Keep a newly prepared webhook disabled until the production route and its signing secret are deployed. Copy all four newsletter variables from `.env.local` into Vercel, deploy, then enable the matching endpoint in Resend → Webhooks. Local environment changes do not update Vercel automatically.

Until the key, segment and sender are configured, homepage subscriptions, registration subscriptions and notice campaigns are preserved locally; drafts and previews work, and custom sending is disabled. Live provider delivery requires those credentials and a verified domain. No additional Vercel cron job is needed.

## Subscriptions and automatic publication

The public form calls `/api/newsletter/subscribe`; `/api/mailchimp` remains a compatibility alias for cached forms. Names and emails are validated and emails normalized; duplicate addresses do not create duplicate contacts. New password accounts stay unverified until authentication confirms their email. New verified OAuth accounts are queued immediately. Background contact synchronization runs after verified registration and public subscription. Existing historical accounts are not enrolled merely by logging in. Provider opt-outs are respected and never reset automatically by registration or repeated form submissions.

Creating or publishing an academy notice writes its unique campaign in the same database transaction. Pending notice content is updated before provider draft creation. Once sending begins, the campaign freezes. Editing or republishing a sent notice does not send another broadcast. Draft, archived, deleted, future and expired notices cannot be sent. Publishing permissions authorize the automatic announcement email; the notice manager's publication control has this effect.

Notice broadcasts link to the full notice and include the notice attachment if supplied. BKF feed refreshes do not send marketing mail. Scheduled notices are queued for their publication time and picked up by the next queue run; the existing daily backup cron is the fallback, so scheduled delivery is not guaranteed to occur at the exact publication minute.

The existing database-backup cron processes a bounded contact/campaign batch **after** backup and billing, with its own error handling and the shared runtime deadline. Admins can also use Process pending. Contacts must finish syncing before campaigns dispatch; provider failures leave recoverable records. Queue throughput is bounded by runtime and provider rate limits. Check the pending contact count after initial setup and use Process pending to drain a backlog.

## Custom newsletters and RBAC

`ADMIN_PANEL:ACCESS` and `EMAIL:READ` are required for every newsletter admin API.

- `EMAIL:CREATE`: create a draft, preview sanitized HTML and upload an attachment.
- `EMAIL:UPDATE`: edit custom drafts or cancel unsent campaigns.
- `EMAIL:APPROVE`: explicitly queue/send a campaign, retry a definite provider rejection, and process pending work.
- Existing `EMAIL:MANAGE` covers all actions through the existing permission resolver.

The migration grants these to existing ADMIN/SUPER_ADMIN roles. Custom roles retain their original grants; assign the actions explicitly in role management. Reading email history alone never allows sending. APIs enforce permissions independently of client controls.

The composer accepts Markdown or HTML, with a branded purple/aqua email shell, mobile layout, unsubscribe footer and sandboxed preview. Unsafe tags, event handlers, scripts and URLs are removed. Up to eight PDF/JPEG/PNG/WebP files (4 MB each) may be uploaded using the existing Cloudflare R2 configuration. Broadcast attachments are **download links**, not binary MIME attachments. Draft uploads are private; stable download routes issue short-lived signed R2 URLs only for attachments used by sending/sent campaigns. Uploads are capped below [Vercel’s request-body limit](https://vercel.com/docs/functions/limitations#request-body-size). Files use a separate `newsletter/attachments/` prefix, preserving backup storage.

Each campaign retains a provider broadcast ID before sending. Concurrent requests claim it atomically. Provider 4xx rejections are shown as failed and may be retried explicitly; ambiguous network/5xx outcomes are held as unknown. The worker reconciles these against the existing provider broadcast. It never blindly resends an uncertain campaign. For an unknown campaign whose provider record still shows draft, review its Resend ID in the provider console; no automatic retry is allowed. A crashed pre-send draft creation can leave an orphan draft in Resend, but cannot send it. Sent means provider acceptance, while individual delivery events appear separately in centralized Email history.
